## 一、四个问题的根因与修法

### 问题 1（P0）新建商品必然失败

根因有两层，缺一不可：

1. src/app/api/products/route.ts 里每个 catch 都调 handleApiError(error)，但这个函数从未 import。
   只要业务流程抛异常，就会变成 ReferenceError: handleApiError is not defined，
   Next 返回空响应体的 500，前端 res.json() 解析失败 → 只剩「操作失败」四个字。
   服务器日志里可以直接看到：⨯ ReferenceError: handleApiError is not defined。
2. 初始库存那段代码还在用 v1.0.2 已废弃的 boxes 表（线上该表 0 行）：
   tx.box.findFirst(...) 必然返回 null → 抛「没有可用的空闲货位」。
   而且它把四段码 A-1-1-1 拆成「货位 A-1-1 + 货位编码」，与 v1.0.2 的四段规范（A-01-01-01）对不上。

修法：

| 位置 | 改动 |
|---|---|
| src/app/api/products/route.ts | 补 import { AppError, handleApiError }；POST 全量重写 |
| 同上 | 初始库存改走 locations + location_stocks + inventory.locationId（与入库过账同一条落库路径） |
| 同上 | 用 normalizeLocationCode() 统一三段/四段编码，找不到货位时返回「货位 A-01-01-01 在该仓库中不存在，请到货架地图确认编码」 |
| 同上 | 用 assertLocationAvailableFor() 做一货位一商品校验，冲突时返回占用方商品名 |
| 同上 | 所有校验失败抛 AppError，前端能拿到具体原因而不是「操作失败」 |

### 问题 2（中）操作日志没有记录

根因：writeLog() 只在商品接口里被调用过，登录、仓库、单位、分类、供应商的写操作从来没有调用；
而商品接口本身又是坏的，所以日志表几乎恒为空。

修法：登录成功 / 登录失败（含失败原因与 IP）、仓库增删改、单位增删、分类增删、供应商增删改全部落库；
writeLog 的 userId 支持字符串（会话里的 id 就是字符串），非法值降级为 null，绝不让日志把主流程带崩。

### 问题 3（低）弹窗关闭后表单残留

根因：onCancel 只 setCreateModalOpen(false)，没有 form.resetFields()，仓库/货位/数量都还留在 state 里。

修法：closeForm() 统一做「关窗 + resetFields + 清空仓库/货位/图片/文件列表」，抽屉加 destroyOnClose，重开一定是干净的。

### 问题 4（低）验证码错误提示不精确

根因：验证码校验在 authorize() 里，NextAuth 会把所有失败统一成 CredentialsSignin，前端拿不到原因。

修法：新增 POST /api/auth/captcha/verify —— 只校验、不消费、按 IP 限流（30 次/分钟）。
登录页提交前先打这个接口：验证码错就明确提示「验证码错误，请重新输入」并自动刷新；
验证码通过后再走 signIn()，账号密码错误仍然是统一文案「账号或密码错误」，
没有引入用户名枚举面（要枚举也得先过验证码）。

### 观察项

- 预置主数据：seed 内置 10 个计量单位（个/件/箱/套/千克/克/米/卷/瓶/袋）与 6 个商品分类，幂等 upsert。
- 宽表格横向滚动：商品表把「图片 + 名称 + 编码」合并成一列（300px），仓库表收窄列宽并把「电话」列设为 lg 以上才显示；
  1280px 视口下「状态 / 操作」列不再被挤出屏幕。

## 三、验证清单（部署后实测）

- 新建商品（SKU-TEST-001 / 单位「个」/ 仓库 + 货位 A-01-01-01 / 初始 100）→ 成功，库存与货架地图同步出现
- 重复编码 → 返回「商品编码「SKU-TEST-001」已存在，请换一个编码」
- 货位不存在 → 返回「货位「A-99-99-99」在该仓库中不存在…」
- 货位被占用 → 返回「货位已被商品「…」占用…」
- 登录成功 / 失败后，「系统日志」页可见记录；建仓库/单位/分类/供应商后「操作日志」页可见
- 关闭新建商品抽屉再打开 → 表单为空
- 验证码输错 → 提示「验证码错误，请重新输入」；密码错 → 「账号或密码错误」
