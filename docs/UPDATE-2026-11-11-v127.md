# v1.2.5 ~ v1.2.7 变更说明（2026-11-11）

> 基线 v1.2.4。这三个版本是连在一起做完的：先把「账实不符」的并发缺陷按住，再补数据安全（备份/日志/邮件模板），
> 最后把「怎么把后续版本送到所有设备上」这件事解决掉，并在此收口为**最后一个开源版本**。
>
> 范围：改的是代码与运维脚本；数据库只做加法，未删除任何业务数据。

---

## 一、v1.2.5 · 并发安全与数据兜底

### 1.1 并发扣库存竞态（P0，最要紧）

**问题**：原实现是「查库存 → 判断够不够 → 写回新数量」三步，`version` 字段只是无条件自增、没参与 `WHERE`，等于假乐观锁；过账状态检查同样是 check-then-act。第三方压测 10 并发实测：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 库存 10，10 单各扣 1 并发过账 | 10/10 成功，库存剩 **8**（丢失 2 次更新） | 10/10 成功，库存 **0** |
| 库存 5，10 单争抢 | 10/10 全成功，**超卖 7 件** | **恰 5 成功 5 拒绝**，库存 0 |
| 同一张单 10 并发过账 | 10/10 全部 POSTED | **1 成功 9 拒绝**，库存只扣 1 |

**修法**（新增 `src/lib/stock-atomic.ts`）：

```sql
-- 扣减：由数据库在行锁内完成判断与扣减
UPDATE inventory SET on_hand = on_hand - ?, version = version + 1
 WHERE id = ? AND on_hand - locked >= ?;

-- 过账抢占：只有抢到状态的那个事务能继续
UPDATE outbound_orders SET status = 'POSTING'
 WHERE id = ? AND status IN ('DRAFT','APPROVED');
```

`affectedRows = 0` 即业务失败，抛 `AppError(400)` 给用户可读提示（「库存不足或已被其他单据占用，请刷新后重试」），不再吐 500。

同一套原子函数也接管了：批次扣减、货位扣减、库存锁定/解锁、调拨发出、盘点结算（并给盘点单加行锁，杜绝重复结算）。

### 1.2 数据备份与回滚

- `src/lib/backup.ts` + `/api/backups`：备份 = `mysqldump`（含触发器）+ `public/uploads` + 配置快照，打包 `tar.gz` 存服务器本地（非 public 目录）。
- 支持手动/定时（每小时 / 每天 / 每周 / 自定义 Cron）、下载、恢复、删除；默认保留 30 天可调，超期自动清理但**始终保留最近一次成功备份**。
- 恢复流程：先生成一次「恢复前安全备份」→ 导入 SQL → 替换 uploads → 写审计；恢复后清理僵尸 `running` 记录。
- 调度靠 `instrumentation.ts` 每 60 秒打一次 `/api/cron/backup`（不直接 import 业务模块，避免 edge 编译问题）。

### 1.3 日志清空留痕

- `/api/logs/clear`：仅管理员可调用，必须传 `confirm="清空日志"`，支持按页签范围清理。
- 清空动作本身写一条系统日志（操作人 / 时间 / 清空条数 / 范围），这条在删除之后写入，不会被自己清掉。

### 1.4 邮件模板中心

- 新增 `mail_templates` 表与 `/api/mail-templates`：编码 / 名称 / 主题 / HTML 正文 / 可用变量。
- 订阅必须绑定模板（后端强校验），正文 `{{变量}}` 按白名单渲染，写错变量在保存时就报错。

- 「当前版本更新内容」区块：从更新中心的版本历史里按本地版本号反查说明，直接显示本版本做了什么。

## 三、v1.2.7 · 更新中心与双通道

### 3.1 更新中心（独立服务）

- 位置：`/opt/cw-update-server`，单文件零依赖，`systemd` 托管，nginx 反代到 `https://update.yuejiaxin.ln.cn`（443 + Let's Encrypt + HSTS）。
- 监听 `127.0.0.1:9958`，外网只走域名；管理面必须登录（Basic Auth）。
- 接口：`GET /api/version?channel=stable|beta`（设备比对）、`GET /api/releases`（版本历史与说明）、`POST /api/publish`（登记直链）、`POST /api/delete`（删除记录）、`POST /api/rollback`（设为最新）。

### 3.2 发布方式改为「登记直链」

- 不再把包上传到更新中心，而是填 1~N 个直链（当前为腾讯云 COS 北京 / 南京 / 成都三地域 + 本机兜底）。
- 设备更新时先对每个直链拉前 256KB 计时，选最快的一路下整包；失败的源直接跳过。
- 关键实现细节：判定可用必须看 `curl` 的**退出码**。早期写成 `t=$(curl ... || true)`，404 时 `-w` 仍输出耗时，导致三个没上传文件的 COS 桶被误判成「最快线路」。

### 3.3 主版本 / 测试版双通道

- `stable`：生产设备默认订阅，只看到稳定版。
- `beta`：验证机订阅，能看到 stable + beta，取版本号最大者（测试通道不会漏掉正式修复）。
- 通道按设备存在 `system_configs`（`category=update, col_key=updateChannel`），由 `/api/system/channel` 读写。

### 3.4 设备侧自更新执行器

`scripts/apply-update.sh`：读元数据 → 多直链测速 → 下载 → sha256 校验 → 备份代码 → 覆盖 → 构建 → 重启 → 预热，`trap ERR` 自动回滚到更新前快照。

**数据库策略**：默认完全不动；仅当包内带 `db-changes.sql` 时执行，且执行前过滤 `DROP` / `TRUNCATE` / `ALTER ... DROP`，只允许建表、加字段、加索引。

**一个踩过的坑**：脚本最初用普通 `spawn` 启动，最后一步 `systemctl restart` 时 systemd 按 cgroup 把脚本一起杀了，状态永远停在 `running`。改为 `systemd-run --unit=cw-update-xxx --collect --type=oneshot` 后，脚本脱离应用 cgroup，重启不再波及自己。

## 四、这套东西的边界（如实记录）

- 更新中心与设备之间是 HTTPS，但**设备站点本身仍是 HTTP**（无域名证书），链路加密待后续补。
- 备份文件以 600 权限存服务器本地，未额外加密。
- 直链依赖对象存储公有读；桶权限收紧时设备会退回本机兜底直链。
- 更新只替换程序代码，**不会迁移历史数据口径**；若某版改了字段含义，需要在发布说明里显式写出。
